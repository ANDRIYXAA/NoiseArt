## 🔧 Інструменти збірки

### CMake

**Що це?** Система автоматичної збірки проєкту.

**Навіщо потрібен?** Уяви, що в тебе 50 файлів `.cpp`. Щоб скомпілювати їх вручну,
тобі потрібно написати довжелезну команду з усіма шляхами. CMake робить це за тебе.

**Як працює?**
1. Ти пишеш файл `CMakeLists.txt` — це "рецепт" збірки
2. CMake читає цей рецепт і генерує файли для твого компілятора
3. Потім компілятор збирає програму

**Аналогія:** CMake — це як шеф-кухар, який дивиться на рецепт (CMakeLists.txt)
і дає команди кухарям (компіляторам) що і в якому порядку готувати.

**Кросплатформність:** На Windows CMake генерує файли для Visual Studio (MSVC),
на Linux — для GCC. Один і той самий `CMakeLists.txt` працює на обох ОС!

**Приклад простого CMakeLists.txt:**
```cmake
# Мінімальна версія CMake
cmake_minimum_required(VERSION 3.20)

# Назва проєкту та мова
project(NoiseArt LANGUAGES CXX)

# Створити виконуваний файл з цих вихідних кодів
add_executable(NoiseArt src/main.cpp)
```

**CMake Presets (CMakePresets.json):**
Щоб не писати довгі команди в терміналі на кшталт `cmake -B build -DCMAKE_TOOLCHAIN_FILE=...`, ми створили файл пресетів. Він зберігає всі налаштування в одному місці (де шукати vcpkg, куди зберігати збірку). Це стандарт сучасного CMake, який підтримують всі IDE (VS Code, Visual Studio, CLion).

**CMakeCache.txt:**
Файл, у якому CMake зберігає результати свого пошуку (наприклад, де знаходиться компілятор або бібліотека). Іноді, якщо щось зламалося (наприклад, ти змінив компілятор чи генератор з Visual Studio на Ninja), цей файл треба **видалити**, щоб CMake почав пошук з чистого аркуша.

### Компілятор C++ (MSVC / GCC)

**Що це?** Програма, яка перетворює код C++ (текст) у машинний код (програму `.exe`).

**MSVC (Microsoft Visual C++)** — компілятор від Microsoft, працює на Windows.
Йде разом з Visual Studio або Build Tools.

**GCC (GNU Compiler Collection)** — компілятор для Linux (і Windows через MinGW).

**Як працює?**
```
Твій код (.cpp) → Компілятор → Об'єктний файл (.obj) → Лінкер → Програма (.exe)
```

1. **Компіляція** — кожен `.cpp` файл перетворюється на `.obj` (машинний код)
2. **Лінкування** — всі `.obj` файли з'єднуються в одну програму `.exe`

**Навіщо два етапи?** Щоб не перекомпільовувати ВСЕ, якщо змінився лише один файл.

---

### vcpkg

**Що це?** Менеджер пакетів (бібліотек) для C++. Як `npm` для JavaScript або `pip` для Python.

**Навіщо потрібен?** Коли тобі потрібна бібліотека (наприклад SDL2), ти можеш:
- ❌ Завантажити вручну, розпакувати, прописати шляхи — складно і муторно
- ✅ Написати `vcpkg install sdl2` — і все готово!

**Як працює?**
1. Встановлюєш vcpkg (один раз)
2. Пишеш `vcpkg install sdl2` — він завантажує і компілює бібліотеку
3. У CMakeLists.txt пишеш `find_package(SDL2)` — і CMake автоматично знаходить SDL2

**Аналогія:** vcpkg — це як інтернет-магазин запчастин. Замість того, щоб самому
виготовляти кожну деталь, ти просто "замовляєш" готову бібліотеку.

## 📦 Бібліотеки

### SDL3 (замість SDL2)

**Повна назва:** Simple DirectMedia Layer 3

**Що це?** Новітня (і набагато краща) кросплатформна бібліотека для роботи з:
- 🪟 Вікнами
- ⌨️ Клавіатурою та 🖱️ Мишкою
- 🎮 Геймпадами та 🔊 Звуком

**Чому ми перейшли з SDL2 на SDL3?**
Під час розробки ми дізналися, що розробники Dear ImGui припинили підтримувати вбудований модуль `sdl2-binding` у нових версіях vcpkg, зосередившись на новітньому **SDL3**. SDL3 має набагато простіший і логічніший API (наприклад, функції повертають `true/false` замість `0 / -1`).

**Аналогія:** SDL3 — це як рамка для картини. Вона створює "полотно" (вікно), а ти (OpenGL + ImGui) малюєш на ньому.

---

### OpenGL

**Повна назва:** Open Graphics Library

**Що це?** API (набір команд) для роботи з відеокартою. Дозволяє малювати
2D та 3D графіку з апаратним прискоренням.

**Навіщо нам?** Щоб швидко відображати зображення у в'юпорті. Відеокарта
малює в сотні разів швидше, ніж процесор.

**Версія 4.6:** Ми використовуємо OpenGL 4.6 — найновіша версія (2017+).
Потребує відеокарту, випущену після ~2012 року (NVIDIA GeForce 400+,
AMD Radeon HD 5000+, Intel HD 4000+). Якщо у тебе комп'ютер 2013 року
або новіший — все буде працювати.

**Що дає 4.6 порівняно з 3.3?**
- **Compute Shaders (з 4.3)** — можна запускати обчислення прямо на відеокарті.
  Це ідеально для нас: ефекти (blur, noise, bloom) можна обробляти на GPU,
  що в 10-100x швидше ніж на процесорі! Ми будемо використовувати це
  для ефектів у майбутньому.
- **Direct State Access (DSA, з 4.5)** — простіший і чистіший синтаксис роботи
  з текстурами, буферами і шейдерами. Менше "магічного" коду.
- **Debug Output (з 4.3)** — вбудоване логування помилок від відеокарти.
  Дуже корисно для навчання — бачиш чіткі повідомлення замість "чорний екран".

**Як працює (спрощено)?**
1. Ти завантажуєш зображення (пікселі) у пам'ять відеокарти → це "текстура"
2. Ти кажеш OpenGL: "Намалюй прямокутник з цією текстурою"
3. Відеокарта робить це миттєво

**Аналогія:** OpenGL — це "мова", якою ти розмовляєш з відеокартою.
Ти їй даєш інструкції, а вона малює.

### Dear ImGui

**Повна назва:** Dear Immediate Mode Graphical User Interface

**Що це?** Бібліотека для створення інтерфейсів (кнопки, слайдери, панелі, меню).

**"Immediate Mode" — що це означає?**
Є два підходи до UI:
- **Retained Mode** (Qt, WinForms): Ти створюєш кнопку один раз, і вона "живе" в пам'яті.
  Щоб змінити текст — шукаєш кнопку і міняєш. Складніше, але ефективніше.
- **Immediate Mode** (ImGui): Кожен кадр ти **заново описуєш** весь інтерфейс.
  Простіше для програміста, ідеально для інструментів/редакторів.

**Приклад коду ImGui:**
```cpp
// Кожен кадр (60 разів на секунду):
if (ImGui::Button("Натисни мене")) {  // Якщо кнопку натиснули
    // зроби щось
}
ImGui::SliderFloat("Яскравість", &brightness, 0.0f, 1.0f);  // Слайдер
```

**Docking Branch** — спеціальна версія ImGui, яка додає:
- Перетягування панелей (як у Photoshop)
- Вкладки (tabs)
- Прикріплення панелей до країв вікна

**Навіщо нам?** Весь UI нашого редактора — панелі шарів, ефектів, в'юпорт —
це Dear ImGui. Вона ідеально підходить для tool-додатків.

### stb_image

**Що це?** Мініатюрна бібліотека для завантаження зображень (PNG, JPG, BMP, TGA, GIF).

**Особливість:** Це ОДИН файл `stb_image.h` (header-only бібліотека).
Не потрібно нічого встановлювати — просто кидаєш файл у проєкт.

**Як працює?**
```cpp
// Завантажити зображення
int width, height, channels;
unsigned char* pixels = stbi_load("photo.png", &width, &height, &channels, 4);

// pixels тепер містить масив кольорів: [R,G,B,A, R,G,B,A, R,G,B,A, ...]
// Кожен піксель = 4 байти (Червоний, Зелений, Синій, Прозорість)
```

**stb_image_write** — парна бібліотека для ЗБЕРЕЖЕННЯ зображень.

**Аналогія:** stb_image — це "перекладач" між файлом (PNG/JPG) та масивом пікселів
у пам'яті, з яким ти можеш працювати.

## 📖 Мовні поняття C++

### Header-файли (.h) та Source-файли (.cpp)

**Навіщо два типи файлів?**

У C++ код розділяється на:
- **Header (.h)** — "оголошення": що існує (назви функцій, класів, їхня форма)
- **Source (.cpp)** — "реалізація": як це працює (тіло функцій)

**Приклад:**
```cpp
// Calculator.h — ОГОЛОШЕННЯ (ЩО є)
class Calculator {
public:
    int add(int a, int b);      // "Є функція add, яка приймає два числа"
    int multiply(int a, int b); // "Є функція multiply"
};
```
```cpp
// Calculator.cpp — РЕАЛІЗАЦІЯ (ЯК працює)
#include "Calculator.h"

int Calculator::add(int a, int b) {
    return a + b;  // Ось як вона працює
}

int Calculator::multiply(int a, int b) {
    return a * b;
}
```

**Навіщо так?** Щоб інші файли могли "побачити" що є Calculator і його методи,
БЕЗ необхідності бачити весь код реалізації. Це прискорює компіляцію і
дозволяє організувати код.

---

### #include та #pragma once

**#include** — це команда "вклей сюди вміст іншого файлу".

```cpp
#include <iostream>       // Системна бібліотека (< >)
#include "Calculator.h"   // Наш файл (" ")
```

**#pragma once** — захист від повторного включення. Без неї, якщо два файли
включають один і той самий `.h`, буде помилка "вже визначено".

```cpp
#pragma once  // "Включи цей файл тільки один раз"

class MyClass { ... };
```

---

### Клас (class)

**Що це?** Креслення для створення об'єктів. Об'єднує дані (змінні) та
функції (методи) в одне ціле.

```cpp
class Dog {
public:                    // public = доступно всім
    std::string name;      // Дані (поле)
    int age;

    void bark() {          // Функція (метод)
        std::cout << name << " каже: Гав!" << std::endl;
    }
};

// Використання:
Dog myDog;
myDog.name = "Бобік";
myDog.age = 3;
myDog.bark();  // "Бобік каже: Гав!"
```

**public / private / protected:**
- `public` — доступно звідусіль
- `private` — доступно тільки всередині класу
- `protected` — доступно класу та його нащадкам

---

### Наслідування (inheritance)

**Що це?** Можливість створити новий клас на основі існуючого.
Новий клас "наслідує" всі дані та методи батьківського.

```cpp
class Animal {              // Батьківський клас
public:
    std::string name;
    void eat() { std::cout << "Їм!" << std::endl; }
};

class Dog : public Animal { // Dog наслідує від Animal
public:
    void bark() { std::cout << "Гав!" << std::endl; }
};

// Dog має і eat() (від Animal), і bark() (свій):
Dog d;
d.name = "Бобік";  // від Animal
d.eat();            // від Animal
d.bark();           // свій
```

**Навіщо нам?** Усі ефекти (Noise, Bloom, Blur) наслідують від базового
класу `Effect`. Це означає, що ми можемо працювати з будь-яким ефектом
однаково, не знаючи його конкретного типу.

---

### Віртуальні функції (virtual)

**Що це?** Функція, яку нащадок може "перевизначити" (замінити своєю версією).

```cpp
class Effect {
public:
    virtual void apply(Image& img) = 0;  // "= 0" означає ОБОВ'ЯЗКОВО перевизначити
    virtual std::string getName() = 0;
};

class NoiseEffect : public Effect {
public:
    void apply(Image& img) override {    // "override" = перевизначаю!
        // Додати шум до зображення
    }
    std::string getName() override {
        return "Noise";
    }
};
```

**`= 0` (чисто віртуальна)** — означає "у базовому класі реалізації НЕМАЄ,
кожен нащадок МУСИТЬ написати свою версію". Такий клас називається **абстрактним**.

**Навіщо нам?** Завдяки цьому LayerStack може зберігати список `Effect*`
і викликати `apply()` для кожного — і кожен ефект зробить щось СВОЄ.

---

### std::vector

**Що це?** Динамічний масив — список елементів, який може змінювати свій розмір.

```cpp
std::vector<int> numbers;       // Порожній список чисел
numbers.push_back(10);          // Додати 10
numbers.push_back(20);          // Додати 20
numbers.push_back(30);          // Додати 30

// numbers = [10, 20, 30]
// numbers.size() = 3
// numbers[0] = 10, numbers[1] = 20
```

**Навіщо нам?** Пікселі зображення зберігаються як `std::vector<uint8_t>`.
Список шарів — як `std::vector<Layer>`.

---

### std::unique_ptr / std::shared_ptr

**Що це?** "Розумні вказівники" — автоматично звільняють пам'ять, коли об'єкт
більше не потрібен.

```cpp
// unique_ptr — ОДИН власник
std::unique_ptr<Dog> dog = std::make_unique<Dog>();
dog->bark();  // Використовуй як звичайний вказівник
// Коли dog виходить з області видимості — пам'ять звільняється автоматично!

// shared_ptr — КІЛЬКА власників
std::shared_ptr<Dog> dog1 = std::make_shared<Dog>();
std::shared_ptr<Dog> dog2 = dog1;  // Тепер двоє "бачать" одного собаку
// Пам'ять звільниться, коли ОСТАННІЙ shared_ptr буде знищений
```

**Навіщо?** У чистому C++ потрібно вручну писати `delete` для кожного `new`.
Якщо забудеш — витік пам'яті. Розумні вказівники роблять це автоматично.

---

### namespace

**Що це?** "Простір імен" — група для організації коду, щоб уникнути конфліктів імен.

```cpp
namespace NoiseArt {
    class Image { ... };    // NoiseArt::Image
    class Layer { ... };    // NoiseArt::Layer
}

namespace SomeOtherLib {
    class Image { ... };    // SomeOtherLib::Image — не конфліктує!
}
```

**Навіщо нам?** Весь наш код буде у просторі імен `NoiseArt`, щоб не конфліктувати
з іменами з бібліотек.

## 🧩 Концепції проєкту

### Game Loop (Головний цикл)

**Що це?** Серце будь-якої графічної програми — безкінечний цикл, який повторюється
~60 разів на секунду (60 FPS).

```
┌──────────────────────────────────────┐
│                                      │
│   ┌─────────────┐                    │
│   │ Обробка     │ ← Натиснув кнопку? │
│   │ подій       │   Рухнув мишу?     │
│   └──────┬──────┘                    │
│          ▼                           │
│   ┌─────────────┐                    │
│   │ Оновлення   │ ← Застосувати     │
│   │ стану       │   ефекти? Зум?     │
│   └──────┬──────┘                    │
│          ▼                           │
│   ┌─────────────┐                    │
│   │ Малювання   │ ← Намалювати UI,  │
│   │ (рендеринг) │   зображення      │
│   └──────┬──────┘                    │
│          │                           │
│          └───── повторити ───────────┘
│
└── Вийти, коли користувач закрив вікно
```

**Навіщо?** Щоб програма "жила" — реагувала на дії і оновлювала зображення.

---

### Система шарів (Layer Stack)

**Що це?** Стек (стопка) ефектів, які послідовно застосовуються до зображення.

```
Оригінальне зображення
        │
        ▼
┌─────────────────┐
│  Шар 1: Noise   │  ← Додає шум
└────────┬────────┘
         ▼
┌─────────────────┐
│  Шар 2: Bloom   │  ← Додає сяйво
└────────┬────────┘
         ▼
┌─────────────────┐
│  Шар 3: Blur    │  ← Розмиває
└────────┬────────┘
         ▼
   Результат 🎨
```

Кожен шар отримує результат попереднього і додає свою обробку.
Шари можна вмикати/вимикати, міняти місцями, видаляти.

---

### Патерн "Реєстр" (Registry Pattern)

**Що це?** Центральне місце, де зареєстровані всі доступні ефекти.

**Навіщо?** Щоб додати новий ефект, ти:
1. Створюєш файл `MyCoolEffect.cpp`
2. Реєструєш його: `registry.add<MyCoolEffect>()`
3. Все! Він автоматично з'явиться в меню UI.

**Без реєстру** довелося б міняти код у 5-10 місцях кожного разу.

```cpp
// EffectRegistry — знає про ВСІ ефекти

    std::vector<EffectInfo> effects;  // Список всіх ефектів

public:
    void registerEffect(EffectInfo info);  // Додати ефект
    std::vector<EffectInfo> getAll();      // Отримати всі
```
